# Application Instruction Understanding Persistence Design

**Date:** 2026-05-06  
**Status:** Approved-for-planning design spec  
**Scope:** Persistent compiled understanding, review artifacts, and cache/invalidation contract for app instruction understanding in `ragenius_app_skeleton` and Builder-facing inspection surfaces.

## Goal

Persist application-instruction understanding as a reusable, versioned artifact per app so the system does not need to re-parse or re-analyze application instructions on every user turn.

The design must support:
- deterministic compiled instruction understanding for runtime use
- optional LLM review of the compiled understanding
- explicit cache invalidation rules
- reuse across sessions and queries
- Builder/admin inspection of the current understanding state

## Non-goals

This design must not:
- replace file-backed markdown instruction storage
- make LLM review the authoritative runtime source of truth
- require recompilation on every chat turn
- redesign `rag_subsystem` retrieval/indexing internals
- require frontend UI changes in the first implementation slice

## Problem Statement

Instruction understanding is app-level metadata, not query-level state.

Today, the system derives understanding at runtime from instruction text and resource bindings, which creates several problems:
- repeated recomputation
- inconsistent behavior when parser logic changes
- no stable artifact to inspect or debug
- no formal notion of “stale” understanding
- no clean place to attach LLM review or human review

The correct model is:
- instruction markdown = source
- compiled understanding = deterministic build artifact
- review summary = optional validation artifact

## Core Design

The system persists two related artifacts:

1. **Compiled Understanding**
- deterministic
- runtime-authoritative
- used by parser/planner/retrieval flow

2. **Review Understanding**
- optional
- advisory
- generated by LLM or human validation
- used for confidence, diagnostics, and inspection

These artifacts are governed by an explicit cache/invalidation contract.

## Compiled Understanding Artifact

This is the authoritative runtime artifact.

### Required metadata

- `app_id`
- `instructions_path`
- `instruction_source_hash`
- `instruction_source_version`
- `parser_contract_version`
- `binding_logic_version`
- `resource_catalog_hash`
- `compiled_status`
- `compiled_at`
- `compile_duration_ms`
- `compile_errors_json`
- `compiled_contract_json`
- `is_active`

### `compiled_contract_json`

This is the deterministic parser/planner contract and must contain at least:
- `instruction_heading_tree`
- `instruction_service_blocks`
- `instruction_procedures`
- `procedure_steps`
- `support_modules`
- `followup_modules`
- `global_policies`
- `resource_catalog_view`
- `default_workflow_inference`
- `parser_warnings`

This artifact is the runtime source used by planner and retrieval.

## Review Understanding Artifact

This is the optional LLM/human review artifact.

### Required metadata

- `app_id`
- `instruction_source_hash`
- `parser_contract_version`
- `review_model`
- `review_prompt_version`
- `review_status`
- `reviewed_at`
- `review_confidence`
- `review_findings_json`
- `review_summary_md`
- `review_recommendations_json`
- `is_active`

### Review semantics

The review artifact may:
- confirm the plausibility of the compiled understanding
- flag likely misclassifications
- identify ambiguous default-workflow inference
- point out suspicious step extraction or resource-binding issues

The review artifact must not automatically replace the compiled contract.

## Human-Readable Snapshot

In addition to structured persistence, the system should write human-readable inspection artifacts.

### Recommended paths

- `ragenius_builder/flask_scaffold/instruction_understanding/{app_id}/understanding.md`
- `ragenius_builder/flask_scaffold/instruction_understanding/{app_id}/understanding.json`

### Purpose

The `.md` snapshot is for:
- debugging
- admin inspection
- diff/review
- understanding why the parser made a specific decision

The `.json` snapshot is optional if the DB already stores the same canonical payload, but it can still be useful for offline diagnostics.

Allowed values:
- `ready`
- `stale`
- `building`
- `failed_compile`
- `superseded`

### Review status

Allowed values:
- `not_reviewed`
- `reviewed_ok`

- `review_failed`
- `review_stale`

### Cache status

Allowed values:
- `hot`
- `missing`
- `invalid`
- `stale_instructions`
- `stale_parser_contract`
- `stale_binding_logic`
- `stale_resource_catalog`

## Cache / Invalidation Contract

The system must rebuild compiled understanding when any input to the compilation pipeline changes.

### Invalidation input set

1. instruction source contents
2. parser contract version
3. binding logic version
4. resource catalog projection

### A. Instruction hash invalidation

Rebuild when:
- `current_instruction_source_hash != cached_instruction_source_hash`

Reason:
- instructions markdown changed

Cache status:
- `stale_instructions`

### B. Parser contract invalidation

Rebuild when:
- `current_parser_contract_version != cached_parser_contract_version`

Reason:
- structural parsing logic changed

Cache status:
- `stale_parser_contract`

### C. Binding logic invalidation

Rebuild when:
- `current_binding_logic_version != cached_binding_logic_version`

Reason:
- planner-side binding semantics changed

Cache status:
- `stale_binding_logic`

### D. Resource catalog invalidation

Rebuild or binding refresh when:
- `current_resource_catalog_hash != cached_resource_catalog_hash`

Reason:
- relevant app-bound resources changed

Cache status:
- `stale_resource_catalog`

## Hash And Version Definitions

### Instruction source hash

Source:
- `instructions/{app_id}/instructions.md`

Method:
- UTF-8 normalized content
- stable line-ending normalization
- `sha256`

### Parser contract version

Manual semantic version string, for example:
- `instruction-parser-2026-05-06-v1`

Must be bumped when changing:
- heading-tree construction
- service-block classification
- default-workflow inference
- heading-style step extraction
- trigger normalization

### Binding logic version

Manual semantic version string, for example:
- `binding-logic-2026-05-06-v1`

Must be bumped when changing:
- step activation semantics
- support-module selection
- follow-up module gating
- supplementary-workflow activation
- resource provenance semantics

### Resource catalog hash

Hash a stable app-scoped projection of builder resources, including:
- `document_id`
- `filename`
- `status`
- `domain`
- `linked_app_id`
- optional `title`

Do not include volatile timestamps.

## Two-Level Refresh Strategy

The system may optionally distinguish:

### Level 1: full structural rebuild

Required when:
- instruction source hash changed
- parser contract version changed

### Level 2: binding refresh

Required when:
- binding logic version changed
- resource catalog hash changed

If implementation simplicity is preferred initially, both levels may trigger the same full rebuild, but the contract should keep the distinction explicit.

## Compile Lifecycle

### Trigger points

Compiled understanding should be checked:
- when an app is first loaded into runtime
- when a new session begins for that app
- when Builder/admin requests inspection
- when explicit “rebuild understanding” is requested

### Resolution sequence

1. read current instruction source
2. compute instruction hash
3. read current parser contract version
4. read current binding logic version
5. compute resource catalog hash
6. fetch active compiled record
7. compare current values to cached values
8. if hot -> use cached compiled understanding
9. if stale or missing -> rebuild and persist new active record

### Supersession behavior

When a new compiled record becomes ready:
- mark prior active compiled record as `superseded`
- keep prior successful record for debugging/history

## Review Lifecycle

### When to run review

Run review when:
- compiled understanding changes
- review model changes
- review prompt version changes
- admin explicitly requests review

### When not to run review

Do not run review:
- on every user query
- as a hard requirement for ordinary runtime execution

### Recommended review mode

Review should usually be asynchronous or admin-triggered unless strict validation is required.

## LLM Review Contract

### Inputs to the review

Provide:
- raw instruction text
- compiled contract JSON
- parser warnings
- default workflow inference
- normalized service-block summary

### Questions the LLM should answer

1. Is the detected default primary workflow plausible?
2. Are support modules likely misclassified?
3. Are follow-up modules likely misclassified?
4. Is any supplementary workflow likely mistaken for support?
5. Are any step boundaries suspicious?
6. Are resource bindings or trigger assumptions likely wrong?

### Structured output

The LLM should return structured review data including:
- `review_confidence`
- `overall_status`
- `default_workflow_assessment`
- `classification_findings`
- `step_extraction_findings`
- `trigger_findings`
- `resource_binding_findings`
- `recommended_actions`

And produce a human-readable `review_summary_md`.

## Runtime Usage Contract

Planner and retrieval should consume:
- the active compiled understanding only

They may optionally read review metadata for warnings, but must not depend on review to function.

### Optional warning behavior

If:
- `review_status = reviewed_with_warnings`
- or `review_confidence` is low

then the runtime may:
- attach internal diagnostics
- expose Builder/admin warnings

but should still use the compiled contract unless explicitly configured otherwise.

## Failure Handling

### Compile failure

If compile fails:
- keep last known good compiled understanding active if available
- persist failed attempt with `compiled_status = failed_compile`
- expose error to admin inspection surfaces

### Review failure

If review fails:
- keep compiled understanding active
- persist `review_status = review_failed`
- do not block runtime

## Service Interfaces

### `get_active_instruction_understanding(app_id)`

Behavior:
1. inspect active compiled record
2. compute current invalidation inputs
3. rebuild if stale/missing
4. return active compiled understanding

### `review_instruction_understanding(app_id, force=False)`

Behavior:
1. fetch active compiled record
2. if review stale or forced, run LLM review
3. persist review result
4. return review artifact

### `get_instruction_understanding_status(app_id)`

Returns:
- compiled status
- review status
- cache status
- stale reasons
- current hashes/versions
- active record identifiers

## Builder/Admin Inspection Contract

Builder/admin inspection should surface:

### Status
- compiled status
- review status
- cache status

### Current version inputs
- instruction hash
- parser contract version
- binding logic version
- resource catalog hash

### Parsed result summary
- detected default workflow
- service blocks
- procedures
- support modules
- follow-up modules
- supplementary workflows
- warnings

### Review summary
- confidence
- findings
- recommended corrections

## Recommended Runtime Policy

### Production runtime
- compiled understanding required
- LLM review optional

### Builder/admin
- may force rebuild
- may force re-review
- should display stale reasons and review findings

### Tests / CI
- deterministic compile required
- LLM review optional and limited to selected fixtures if enabled

## Success Criteria

This design is complete when:

1. application-instruction understanding is persisted per app as a structured compiled artifact
2. the artifact is reused across user queries and sessions
3. cache invalidation is driven by explicit hashes/versions, not by timestamps or user turns
4. LLM review is available as an optional validation layer
5. runtime remains deterministic even if review is missing or fails
6. Builder/admin can inspect current compiled/review/cache status for any app
